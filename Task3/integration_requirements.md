# Требования к интеграции с платформой «Умный дом»

Требования относятся к интеллектуальному домофону и шлагбауму и учитывают актуальные диаграммы контекста и контейнеров. Протоколы аутентификации и ограничения ниже — предлагаемые условия интеграции, которые необходимо согласовать с партнёром.

## Безопасность

1. Все API и webhook должны работать по HTTPS с TLS 1.2 или выше и проверкой сертификатов. Внешние подключения к PropDevelopment проходят через firewall; партнёру доступен только выделенный endpoint `smart-home-service`, без прямого доступа к CRM и базам данных. Для WebRTC согласовываются отдельные сетевые правила.
2. `tenant-core-app` должен проверять право пользователя на конкретное действие с конкретным устройством по актуальной связи с домом и УК. Платформа партнёра также должна ограничивать доступ согласованными домами и устройствами. Подмена идентификатора пользователя, дома, УК или устройства не должна давать доступ к чужим данным, видеозвонкам и командам.
3. Передавать партнёру только необходимые идентификаторы пользователей, домов и устройств, разрешения со сроками действия и номера автомобилей. ФИО, контакты, сведения о сделках и платежах в эти контракты не включать. Состав запросов и webhook проверять по согласованной схеме, ограничивать размер сообщений и частоту обращений.
4. Биометрические данные должны обрабатываться в контуре партнёра и не попадать в `tenant-core-db`, журналы и DWH PropDevelopment. До включения распознавания лиц согласовать порядок получения и отзыва согласия, подключения пользователя, удаления биометрии и ответственность сторон. Сохранить возможность пользоваться домофоном без распознавания лица.
5. Данные у партнёра и в PropDevelopment должны быть защищены при хранении. Секреты и ключи хранить вне кода и мобильного приложения, предусмотреть их ротацию и отзыв. Запретить запись токенов, биометрии и видеопотоков в технические журналы; установить сроки хранения разрешений, номеров автомобилей и событий и порядок удаления данных у обеих сторон.
6. Для команд, изменений разрешений и событий вести защищённый от изменения журнал: инициатор, дом, устройство, время, идентификатор операции и результат. Предусмотреть оповещения о массовых отказах авторизации, ошибках синхронизации и недоступности партнёра.

## Аутентификация и авторизация

| Канал                                        | Требование |
|----------------------------------------------| --- |
| Мобильное приложение -> PropDevelopment      | Аутентификация через существующий `auth-service-1` на Keycloak. Для приложения использовать Authorization Code с PKCE и системный браузер. Доступ к API — по access token; ID token не использовать для вызова API. |
| `smart-home-service` -> партнёр              | OAuth 2.0 Client Credentials с отдельной сервисной учётной записью и mTLS для аутентификации клиента. Разделить полномочия на открытие устройств, управление разрешениями и создание видеосессий; ограничить их домами и устройствами интеграции. |
| Партнёр -> webhook `smart-home-service`      | Взаимная TLS-аутентификация по выделенному сертификату партнёра. Endpoint разрешает только отправку событий; изменение разрешений и выполнение команд через него запрещены. Проверять идентификатор события и время отправки для защиты от повторов. |
| Мобильное приложение <--> платформа партнёра | После проверки прав в `tenant-core-app` выдавать через адаптер краткоживущее разрешение на конкретную видеосессию. Партнёр должен проверять пользователя, вызов и срок действия разрешения. Оно не даёт права управлять дверью или шлагбаумом. |

Для OAuth 2.0 применять требования безопасности RFC 9700: ограничивать срок действия и получателя токена, защищать refresh token и использовать PKCE. Получатели JWT должны проверять подпись, издателя, получателя, срок действия и полномочия; успешная проверка токена не заменяет проверку доступа к устройству.

## Взаимодействие систем

1. Текущее мобильное приложение передаёт команды открытия двери и управления шлагбаумом в `tenant-core-app` по HTTPS REST. Сервис проверяет права с учётом данных CRM, хранит разрешения, привязки пользователей и автомобилей и журнал операций в `tenant-core-db`. Затем передаёт разрешённую операцию в `smart-home-service` по HTTPS REST; адаптер вызывает API партнёра.
2. Выдачу, изменение и отзыв разрешений передавать тем же путём. `tenant-core-app` хранит желаемое состояние и подтверждение синхронизации с партнёром. Автоматическое открытие по лицу или номеру выполняется платформой партнёра только по действующему разрешению. До запуска согласовать предельный срок доставки отзыва и срок действия локальных разрешений; после их истечения или при отсутствии действующего разрешения автоматическое открытие запрещено.
3. Партнёр отправляет вызовы домофона, события доступа и результаты команд в `smart-home-service` через HTTPS webhook. Адаптер проверяет отправителя, формат сообщения и принадлежность устройства, затем передаёт событие в `tenant-core-app`. Сервис сохраняет событие и доставляет его только соответствующему пользователю через WSS. API должно позволять получить пропущенные события после восстановления соединения.
4. Параметры видеосессии проходят через адаптер и `tenant-core-app` в приложение. Аудио и видео передаются непосредственно между приложением и платформой партнёра по WebRTC с DTLS-SRTP, как на диаграмме контейнеров. Команда открытия двери проходит отдельно через `tenant-core-app` с повторной проверкой прав.
5. Контракты API должны содержать версии, форматы ошибок, идентификаторы команд и событий, время создания и срок актуальности. Для команд использовать ключ идемпотентности: повтор запроса с тем же ключом не должен повторно открывать устройство. Webhook подтверждать после надёжного сохранения события; партнёр повторяет доставку при ошибке, получатель исключает дубликаты и учитывает порядок версий разрешений.
6. Установить тайм-ауты и ограниченные повторы с увеличением интервала. При неоднозначном результате открытия запрашивать статус исходной команды, а не создавать новую; просроченные команды не исполнять. Приложение должно различать принятие команды и подтверждённое выполнение. После сбоя сверять разрешения с партнёром и восстанавливать пропущенные события; недоступность интеграции не должна выдавать новые права доступа.
